The Engine needs two callback functions (or trait methods) to bridge between the generic `SM::Event` / `SM::State` types and the opaque bytes stored in SQLite:

```rust
// Client provides these to bridge typed events <-> opaque bytes
pub trait Codec: Send + Sync + 'static {
    type Cursor: ChainCursor;
    type Event: Send + 'static;
    type State: Clone + Send + 'static;

    /// Convert a library Event to storage representation (cursor tuple + payload bytes)
    fn encode_event(&self, event: &Event<Self::Cursor, Self::Event>) -> (i64, i64, Vec<u8>);

    /// Convert storage representation back to a library Event
    fn decode_event(&self, stored: &StoredEvent) -> Option<Event<Self::Cursor, Self::Event>>;

    /// Serialize state to opaque bytes for snapshot storage
    fn encode_state(&self, state: &Self::State) -> Vec<u8>;

    /// Deserialize state from opaque bytes (may fail for corrupt/incompatible snapshots)
    fn decode_state(&self, bytes: &[u8]) -> Option<Self::State>;

    /// Convert a cursor to (major, minor) i64 tuple for storage
    fn cursor_to_tuple(&self, cursor: &Self::Cursor) -> (i64, i64);

    /// Convert (major, minor) tuple back to cursor
    fn tuple_to_cursor(&self, major: i64, minor: i64) -> Self::Cursor;
}
```

The Codec trait keeps the Engine generic — it doesn't know how to serialize/deserialize events or state. The client provides this alongside their StateMachine implementation.

**Engine methods:**

```rust
impl<SM, S> Engine<SM, S> {
    /// Process a batch of new events: write to storage, then apply to ReducerCore.
    /// Returns the number of events actually stored (dedup may reduce this).
    pub fn process_events(&mut self, events: &[Event<SM::Cursor, SM::Event>]) -> Result<usize, ...>;

    /// Get a watch::Receiver for the current state.
    pub fn subscribe(&self) -> watch::Receiver<SM::State>;

    /// Get the current state.
    pub fn state(&self) -> SM::State;
}
```

In `process_events`:
1. Convert events to StoredEvents via codec.encode_event
2. Call storage.write_events(source_id, &stored_events) — get inserted count
3. Build an Anchor with the last event's cursor
4. Call storage.write_anchor (in same transaction if SqliteStorage exposes write_events_and_anchor)
5. Update coverage: storage.add_coverage(source_id, first_cursor, last_cursor)
6. Apply each event to ReducerCore via core.apply(&event) — the write-first invariant
7. Increment events_since_snapshot by inserted count (NOT batch size — Pitfall 4)
8. If events_since_snapshot >= config.snapshot_every_n: create snapshot via codec.encode_state, call storage.write_snapshot, reset counter

CRITICAL: The coordinator has two distinct code paths per research Pitfall 5:
- `process_new_events()`: write to storage THEN apply to ReducerCore (for new events)
- `replay_stored_events()`: apply to ReducerCore only, NO storage write (for recovery)

**Step 1: Create src/coordinator/recovery.rs:**

The recovery pipeline follows the exact sequence from research Pattern 8:

```rust
pub async fn recover<SM, S, ES, C>(
    engine: &mut Engine<SM, S>,
    source: &ES,
    codec: &C,
    live_tip: &SM::Cursor,
) -> Result<(), RecoveryError>
where
    SM: StateMachine,
    S: Storage,
    ES: EventSource<Cursor = SM::Cursor, Event = SM::Event>,
    C: Codec<Cursor = SM::Cursor, Event = SM::Event, State = SM::State>,
{
    // 1. Load latest snapshot
    let snapshot_cursor = load_snapshot(engine, codec)?;

    // 2. Replay cached events from snapshot_cursor to cached_tip
    let cached_tip = replay_cached_events(engine, codec, &snapshot_cursor)?;

    // 3. Fetch gap: from cached_tip (or snapshot_cursor) to live_tip
    let gap_start = cached_tip.unwrap_or_else(|| codec.cursor_to_tuple(&snapshot_cursor));
    fetch_gap(engine, source, codec, gap_start, live_tip).await?;

    Ok(())
}
```

**load_snapshot:**
1. Query `storage.latest_snapshot(source_id)`
2. Try `codec.decode_state(snapshot.payload)` — if fails:
3. Query `storage.snapshots_before(source_id, snapshot.cursor)` for older snapshots
4. Try each in order until one deserializes
5. If none work: call `source.fetch_state(genesis_cursor)` for initial state
6. Create ReducerCore with the recovered state

**replay_cached_events:**
1. Query `storage.events_in_range(source_id, snapshot_cursor, cached_tip)`
2. For each event: decode via `codec.decode_event`, apply to ReducerCore via `replay_stored_events` (NOT process_new_events — Pitfall 5)
3. Return the cursor of the last replayed event (or None if no cached events)

**fetch_gap:**
1. Loop: call `source.fetch_events(gap_start_cursor, live_tip)` in chunks
2. For each chunk: call `engine.process_new_events(chunk)` — this writes to storage + applies
3. Advance gap_start to the cursor of the last event in the chunk
4. Stop when fetch_events returns empty (gap closed) or gap_start >= live_tip
5. This is INGEST-02 (chunked fetch) and INGEST-03 (gap stitching)

Important: The coordinator handles the async bridge. Since Storage is sync and the recovery function is async (because EventSource is async), use `tokio::task::spawn_blocking` for storage calls if running in an async context. Alternatively, for the Phase 2 implementation where the coordinator is the only caller, call storage methods directly (they're sync and fast).
