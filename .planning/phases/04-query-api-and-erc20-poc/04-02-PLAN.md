<objective>
Implement historical query capabilities: At(cursor) with 4-tier reconstruction planner, Range(from, to) with lazy batch-paginated iteration, and the underlying Storage extension for height-range queries.

Purpose: At() is the core historical query — it materializes state at any past cursor position using the cheapest available path. Range() enables efficient iteration over event history without loading everything into memory. Together with Plan 01's Current()/OnChange(), this completes the full query API.

Output: HistoricalStore trait, reconstruction planner, EventRangeIterator, Storage::load_events_by_height_range, integration tests covering all reconstruction tiers and lazy pagination.
</objective>

2. Implement in `InMemoryStorage` (src/storage/memory.rs):

   - Sort by height ascending
   - Flatten events from matching blocks
   - Apply offset/limit to the result
   - Return (cursor_bytes, payload_bytes) from inner.events entries

3. Implement in `SqliteStorage` (src/storage/sqlite.rs):
   ```sql
   SELECT e.cursor_bytes, e.payload_bytes
   FROM events e
   JOIN blocks b ON e.block_hash = b.hash
   JOIN canonical_tips ct ON ct.block_hash IS NOT NULL
   WHERE b.height >= ?1 AND b.height <= ?2
     AND b.source_id = ?3
   ORDER BY b.height ASC, e.id ASC
   LIMIT ?4 OFFSET ?5
   ```
   Note: The exact join to ensure we only get canonical chain events needs care. The canonical chain is the path from canonical_tip backward via parent pointers. A simpler approach: since blocks on non-canonical branches exist in storage, we need to filter to only canonical blocks. One approach: walk canonical_chain in Rust (using collect_canonical_chain), then query events for those block hashes. For pagination this is tricky. Alternative: for Range() queries, first call collect_canonical_chain to get the ordered list of canonical block hashes in the range, then paginate over events from those blocks. This is what InMemoryStorage does anyway.

   Actually, the simplest correct approach for both impls: use collect_canonical_chain to get canonical block hashes, filter by height range, then load events for those blocks with pagination. This avoids complex SQL joins and ensures correctness (only canonical chain events).

   Revised approach for SqliteStorage: given that collect_canonical_chain already exists and returns blocks in forward order, the implementation can:
   - Call collect_canonical_chain([0;32], tip) to get full canonical chain
   - Filter to blocks in height range
   - Load events for those blocks sequentially with pagination tracking

   But this loads the full chain hash list which could be expensive. Better approach: add a helper that walks canonical chain from tip backward, collecting only blocks in the height range. Or: use SQL to get blocks that ARE on the canonical chain. The canonical chain is defined by parent pointer traversal from the tip. Without a "canonical" column on blocks, we can't do a simple SQL WHERE clause.

   Pragmatic approach for MVP: `load_events_by_height_range` uses `collect_canonical_chain([0;32], tip_hash)` internally, then slices to the height range, then loads events for those blocks with offset/limit tracking. This works for both InMemoryStorage and SqliteStorage. Performance optimization (adding a canonical flag column) is future work.

   For SqliteStorage specifically, this means: get_canonical_tip, collect_canonical_chain, filter by height, load_block_events for each block in range, apply offset/limit across the accumulated results. The lock is released between each load_block_events call naturally since each call acquires/releases the Mutex.

4. Build the reconstruction planner in `src/store/mod.rs`. This is an async function (not on the Store trait, since Store::get() is sync). Design as a standalone async function or a method on a separate `HistoricalStore` trait:

   ```rust
   /// Trait for stores that support historical queries.
   /// Separate from Store because at() is async (may need RPC fallback).
   #[async_trait::async_trait]
   pub trait HistoricalStore: Store {
       /// Reconstruct state at a historical cursor position.
       /// Uses the cheapest available path (4-tier cost hierarchy).
       async fn at(&self, cursor: &<Self as Store>::State, ...) -> Result<Self::State, ...>;
   }
   ```

   Actually, the cursor type is not part of Store::State. The at() function needs access to storage, codec, source, and the state machine. It's more like a free function that takes all these components. Design:

   ```rust
   /// Reconstruct state at a given block height using the cheapest path.
   ///
   /// Cost hierarchy:
   /// 1. Exact snapshot at target block -> return directly
   /// 2. Nearest snapshot + cached event replay to target
   /// 3. Nearest snapshot + fetch missing events + replay to target
   /// 4. Direct fetch_state from source (if available)
   ///
   /// Falls through tiers until state is materialized.
   pub async fn reconstruct_at<SM, S, ES, C>(
       storage: &S,
       source: &ES,
       codec: &C,
       sm: &SM,
       initial_state: &SM::State,
       source_id: &str,
       target_height: u64,
   ) -> Result<SM::State, EngineError>
   ```

   Implementation:
   - Get canonical tip from storage
   - Find the block hash at target_height by walking canonical chain (need a way to find block by height on canonical chain — walk from tip back to target)
   - Try find_nearest_snapshot on the canonical chain up to that block
   - If snapshot exists at exact target block: decode and return (tier 1)
   - If snapshot exists before target: decode state, collect_canonical_chain from snapshot to target, load_block_events for each, replay through SM::apply (tier 2)
   - If no snapshot or blocks missing in range: use fetch_blocks from source for the gap, process them, then replay (tier 3)
   - If none of the above works: call source.fetch_state() with cursor at target (tier 4)

   Note: Need a helper to find the block hash at a specific height on the canonical chain. The current Storage trait doesn't have `get_block_by_height`. Options:
   - Walk canonical chain from tip backward until reaching target height
   - Add a get_block_hash_at_height method to Storage

   For now: walk backward from tip. This is O(chain_length) worst case but correct. Can be optimized later with a height index.

5. Build `EventRangeIterator` in `src/store/mod.rs`:
   ```rust
   pub struct EventRangeIterator<S: Storage, C: Codec> {
       storage: Arc<S>,
       codec: Arc<C>,
       source_id: String,
       from_height: u64,
       to_height: u64,
       page_size: usize,
       offset: usize,
       buffer: Vec<Event<C::Cursor, C::Event>>,
       buffer_pos: usize,
       exhausted: bool,
   }
   ```
   Implements `Iterator<Item = Event<C::Cursor, C::Event>>`. When buffer is consumed, loads next page via `storage.load_events_by_height_range()`, decodes via codec, refills buffer. Returns None when no more pages.

   CRITICAL: rusqlite Rows borrows Connection. The batch-pagination pattern (load page into Vec, release lock, yield from Vec) avoids holding the lock across iteration. load_events_by_height_range acquires and releases the Mutex internally per call.
